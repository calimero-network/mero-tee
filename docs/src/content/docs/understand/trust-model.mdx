Trust in the storage-key flow is **bidirectional**. Before the KMS releases a
node's storage key, the node proves it runs an approved image inside genuine TDX
hardware; and the KMS exposes its own quote so the node can prove the KMS is
genuine first. Neither side relies on TLS identity or operator trust alone — the
root of trust is the Intel TDX quote signed by the CPU.

:::note
This page covers the **node ⇄ KMS** storage-key relationship implemented in this
repo (`mero-kms/`). The separate `ReadOnlyTee` **fleet admission** trust flow
lives in Calimero Core — see
[TEE Attestation & Fleet Admission](https://calimero-network.github.io/core/protocol/tee-attestation/).
:::

## Plane 1 — the node verifies the KMS

The KMS is stateless and holds no long-term secret of its own, but a node should
still confirm it is talking to a real KMS enclave before sending a key request.
The KMS provides `POST /attest` for exactly this: the caller sends a fresh 32-byte
nonce, and the KMS asks dstack for a TDX quote whose `report_data` is
`nonce ‖ binding` (`mero-kms/src/handlers/attest.rs`). The caller then checks the
quote's signature, the nonce binding, and the KMS's own measurements against
known-good values.

```
report_data[0..32]  = client nonce            (freshness)
report_data[32..64] = binding                 (defaults to SHA-256("mero-kms-phala-attest-v1"))
```

The same endpoint powers the public [attestation verifier](/flows/verification/).

:::caution
`/attest` proves the KMS is a genuine TDX enclave running a specific measurement.
It does **not** by itself authenticate the caller or release anything — key
release is gated separately in Plane 2. Whether a given `merod` client enforces
Plane 1 before requesting a key is a client-side decision; the KMS's role is to
make an honest quote available.
:::

`merod` enforces it whenever a node is pointed at a release (`tee-release-version`
on the node images): the KMS's TCB status and MRTD/RTMR0–3 must be in the signed
release policy's `kms_allowed_*` allowlists, **and** the `compose-hash` its RTMR3
event log measures must be in `kms_allowed_event_payload`. merod replays the
`eventLog` `/attest` returns, recomputing every RTMR3 event digest from its
contents, and trusts the compose hash only when the replay reproduces the quote's
RTMR3. A policy with no compose hash is refused. See
[the derivation root](#the-derivation-root-the-dstack-app) for why registers
alone are not enough.

## The derivation root: the dstack app

A node's storage and data-disk keys are a pure function of the KMS's dstack
**app** key and the path `{namespace}/{profile}/{peerId}`
(`mero-kms/src/handlers/get_key.rs`). mero-kms only decides *when* to ask dstack
for one. So anything that runs under the same app ID can derive every node's
keys without going through mero-kms at all:

- **The app owner.** They can upgrade the app to another compose file — a debug
  image with a shell, or a one-line `get_key` endpoint — and call
  `get_key("merod/storage/locked-read-only/<peerId>")` from inside it.
- **A sibling deployment.** A `debug` KMS running under the `locked-read-only`
  app's ID has a shell and the locked app key.
- **dstack's KMS itself**, which holds the app key's root.

Sealed key release protects a key in transit; it cannot protect a key against
its own derivation root. Three controls narrow who holds that root
([#338](https://github.com/calimero-network/mero-tee/issues/338)):

| Control | What it stops | Where |
| --- | --- | --- |
| **merod pins the KMS compose hash** | A node trusting a KMS app upgraded to an unreleased compose file, even one whose registers are allowlisted | `merod` (core), `kms_allowed_event_payload` in the signed policy |
| **One dstack app ID per profile** | A debug KMS, with a shell, sharing the locked KMS's app key | [Deploy the Phala KMS](/operate/runbooks/#deploy-the-phala-kms) |
| **On-chain compose-hash allowlist on the locked app** | The owner silently upgrading the locked app: an upgrade has to add a compose hash in public, on the app's contract, first | [Deploy the Phala KMS](/operate/runbooks/#deploy-the-phala-kms) |

The node-side pin runs in code on every key fetch. The other two are
deployment controls, and the pin only fully works with them: a compose hash
names a compose file, not an app, so the pin says *what* the KMS runs, and the
app-ID split plus the on-chain allowlist say *who else* can run code with its
key. What remains is dstack's KMS and, for the on-chain allowlist, whoever
controls the app contract's owner key — which is why that should be a multisig,
not a deployer's hot wallet.

### Considered: a node-contributed secret

Mixing a secret only the node holds into the key would take the dstack root out
of the trust base for confidentiality: `key = HKDF(kms_key, node_secret)`, with
the KMS half released as today. It is **not adopted yet**, because the only
place a TD can keep a secret across reboots is the disk the key protects, and
every choice of where to keep it gives something up:

- **Sealed to the TD's measurements** (a key derived from MRTD/RTMRs): survives
  reboots, but an image upgrade changes the measurements, and the node can no
  longer open its own data. Upgrades would need an in-TD re-key before reboot.
- **Kept by a second, independent KMS** (for example a different dstack app, or
  a different provider): two roots must collude instead of one. This is the
  most practical option, at the cost of a second service on the key path.
- **Generated at first boot and held only in memory**: no root can derive it,
  but a reboot loses the data, which rules it out for a replica with state.

If a second KMS is adopted, the migration is additive and keyed off the
existing store:

1. Ship merod that can fetch both halves and derive `HKDF(k1, k2)`, still
   opening stores created under `k1` alone. A store records which scheme it
   uses (a version in its KMS key metadata), never inferred.
2. New nodes create stores under the combined key.
3. Existing nodes re-encrypt in place — open with `k1`, write under
   `HKDF(k1, k2)`, swap atomically — and only then record the new scheme. A node
   that crashes midway reopens with whichever key its recorded scheme names.
4. Once the fleet has migrated, a later merod refuses the `k1`-only scheme on
   `locked-read-only`. A node still on it has to be recreated.

The data disk (LUKS2) follows the same steps with a second keyslot: add the
combined key's slot, then remove the old one.

## Plane 2 — the KMS verifies the node

Key release (`POST /get-key`, `mero-kms/src/handlers/get_key.rs`) never trusts a
request without a fresh, signed, hardware-attested proof bound to the node's peer
identity. The steps, in order:

1. **Challenge.** The node calls `POST /challenge { peerId }`. The KMS stores a
   single-use random 32-byte nonce keyed by a `challengeId` with a TTL
   (`CHALLENGE_TTL_SECS`, default **60s**) and returns
   `{ challengeId, nonceB64, expiresAt }`.
2. **Quote + signature.** The node generates a TDX quote whose `report_data` is
   `nonce ‖ SHA-256(peerId)`, and signs a canonical payload binding the
   `challengeId`, nonce, a hash of the quote, and the `peerId` with its libp2p
   private key.
3. **Key request.** The node calls
   `POST /get-key { challengeId, quoteB64, peerId, peerPublicKeyB64, signatureB64 }`.
4. **Challenge consumed.** The challenge is consumed **before** any crypto check,
   so a replay always fails on the second attempt regardless of where the first
   failed.
5. **Signature check.** The KMS confirms the supplied public key derives to the
   claimed `peerId`, then verifies the signature over the canonical payload.
6. **Quote check.** The quote is verified (DCAP signature), and its `report_data`
   must contain the issued nonce **and** `SHA-256(peerId)`.
7. **Policy check.** The quote's TCB status and all five measurement registers
   (MRTD, RTMR0–3) are checked against the loaded attestation policy.
8. **Key derivation.** On success the KMS asks dstack to derive the key at path
   `{KEY_NAMESPACE_PREFIX}/{profile}/{peerId}` (default prefix `merod/storage`)
   and returns `{ key }`. Derivation is deterministic — the same node always
   receives the same key.

Because the profile is part of the derivation path, a debug node and a production
node with the same `peerId` receive **different** keys even from the same KMS.

## The attestation policy

The policy is loaded at startup (from a signed release, or from `ALLOWED_*` env
vars in explicit `USE_ENV_POLICY` mode) and modelled as
(`mero-kms/src/policy.rs`):

```rust
struct AttestationPolicy {
    enforce_measurement_policy: bool,
    allowed_tcb_statuses: Vec<String>, // normalized lowercase, e.g. ["uptodate"]
    allowed_mrtd:  Vec<HexMeasurement>,
    allowed_rtmr0: Vec<HexMeasurement>,
    allowed_rtmr1: Vec<HexMeasurement>,
    allowed_rtmr2: Vec<HexMeasurement>,
    allowed_rtmr3: Vec<HexMeasurement>,
}
```

In the release-policy JSON the register keys are `node_allowed_mrtd`,
`node_allowed_rtmr0..3`, and `node_allowed_tcb_statuses`, with legacy
`allowed_*` names accepted as a fallback. Each measurement is a 48-byte
(96-hex-char) SHA-384 value.

:::caution[Fail-closed]
When `ENFORCE_MEASUREMENT_POLICY` is true (the default), startup validation
requires **every** register allowlist — MRTD *and* all four RTMRs — plus the TCB
allowlist to be non-empty, or the service refuses to start
(`validate_policy_requirements`). At request time an empty allowlist for any
register also rejects the quote. A misconfigured policy fails closed rather than
admitting everything.
:::

## What each measurement pins

| Register | What it measures | Notes for this system |
| --- | --- | --- |
| `MRTD` | SHA-384 of the initial VM image at launch | Pins the exact node/KMS image. |
| `RTMR0` | Firmware (TDVF) measurement | Extended during early boot. |
| `RTMR1` | OS kernel / boot measurement | Extended during kernel boot. |
| `RTMR2` | Application / kernel-cmdline measurement | The node image injects `calimero.root_hash` (a hash of `/etc/calimero`, baked binaries, and grub config) into the kernel cmdline, measured here (`mero-tee/playbook.yml`). It is computed at build time and measured as a **string**: nothing at boot re-hashes those files against it, so it identifies the image but does not stop an offline edit of the boot disk ([#334](https://github.com/calimero-network/mero-tee/issues/334)). |
| `RTMR3` | Runtime events after boot | Carries the profile/role separation: the KMS extends it with `calimero.kms.profile=<profile>`; the node image's `calimero-init` extends it with role + profile + root hash. |

### RTMR3 profile cohort separation

Each image **profile** (`debug`, `debug-read-only`, `locked-read-only`) produces
a distinct RTMR3 value. A production KMS policy lists only the production RTMR3,
so a debug node's quote is rejected. The separation is enforced by hardware —
there is no software path to forge an RTMR3 value — and reinforced by the profile
being baked into the key-derivation path.

## Threat mitigations

| Threat | Mitigation |
| --- | --- |
| **Rogue KMS** | A fake KMS cannot produce a valid quote with the expected KMS measurements; Plane 1 verification via `/attest` rejects it. |
| **KMS app upgraded to another compose file** | merod replays the KMS's RTMR3 event log and refuses any compose hash not in the signed policy's `kms_allowed_event_payload`; the locked app's on-chain allowlist makes an upgrade public before it can run. |
| **Debug KMS sharing the locked app key** | Each profile's KMS runs under its own dstack app ID, and each profile's compose file (and so its compose hash) differs. |
| **Rogue / tampered node** | A node outside TDX cannot produce a valid quote; a tampered image has different MRTD/RTMR values that the policy rejects. |
| **Replay** | The challenge nonce is single-use and TTL-bound and is consumed before verification; the `/attest` nonce prevents quote reuse. |
| **Peer-ID spoofing** | `get-key` requires a signature by the key that derives to the claimed `peerId`, and binds `SHA-256(peerId)` into the quote's `report_data`. |
| **Profile escalation** | Distinct hardware-measured RTMR3 per profile; the policy rejects any RTMR3 not on its allowlist. |
| **Host reads or edits a node's disk** | The data disk is LUKS2 with dm-integrity, keyed by `merod kms disk-key` from the KMS under the same attestation as the storage key; the disk-unlock identity sits in the LUKS2 header and is useless without a genuine TD. merod's store keeps its own KMS key on top. |
| **Policy downgrade via metadata** | `tee-release-version` is operator-set, and every release's policy is validly signed. The image bakes its own version as a floor (`/etc/calimero/min-tee-release-version` → `MERO_TEE_MIN_VERSION`); `calimero-init` and merod both refuse an older release. |
| **Policy tampering** | The release policy can be pinned by SHA-256 (`MERO_KMS_POLICY_SHA256`); a mismatch aborts loading. |

Rejections surface as typed errors — `tcb_status_rejected` and
`measurement_policy_rejected` return **403**, challenge/signature/attestation
failures return **401**, and an unloaded policy returns **503**. See
[error handling](/operate/error-handling/) for the full mapping.
